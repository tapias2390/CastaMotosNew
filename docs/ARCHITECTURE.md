# Arquitectura — CASTAMOTO

## Capas (Hexagonal / Clean + MVC)

```
Frontend (estático, /frontend)
    ↓ fetch/AJAX
API REST (/api/*)
    ↓
Router (Infrastructure/Http/Router.php)
    ↓
Controllers (Presentation/Controllers)
    ↓
Application (casos de uso — se puebla desde la Fase 2 en adelante)
    ↓
Domain (entidades y reglas de negocio puras — se puebla desde la Fase 3)
    ↓
Repositories (Infrastructure — acceso a datos vía PDO)
    ↓
Database (MySQL/MariaDB)
```

## Flujo de una petición a la API

1. El navegador pide `GET /api/health`.
2. El `.htaccess` de la raíz reescribe la URL hacia `backend/public/index.php?__route=api/health` (sin depender del subdirectorio de despliegue).
3. `backend/public/index.php` inicializa `Config`, `Logger`, registra las rutas de `routes/api.php` y delega en `Kernel`.
4. `Kernel` aplica CORS, construye el `Request` desde las superglobales y llama a `Router::dispatch()`.
5. `Router` hace match del patrón (`api/health`) contra la ruta registrada y llama al controlador correspondiente.
6. El controlador responde con `Response::success()`/`Response::error()`, que siempre siguen el formato `{ success, message, data|errors }`.
7. Cualquier excepción no controlada es capturada centralmente por `Kernel`, registrada en `storage/logs` y devuelta como JSON consistente (ocultando detalles internos si `APP_ENV=production`).

## Autenticación y autorización (Fase 2)

```
Request
    ↓
Router::dispatch()
    ↓
middleware[] (en orden, ej. AuthMiddleware)
    ↓ Request enriquecido (withAttribute('auth_user', User))
Controller
```

- `AuthMiddleware` exige `Authorization: Bearer <jwt>`, lo valida con `JwtService` (firebase/php-jwt) y adjunta la entidad `User` autenticada al `Request` (inmutable: `withAttribute()` devuelve una copia).
- El payload del JWT solo lleva `sub` (id) y `roles`; los **permisos** se resuelven consultando `role_permission` en cada petición (vía `RequirePermissionMiddleware`, listo para las Fases 9/10), así un cambio de permisos no depende de que expire el token.
- Los casos de uso (`Application/UseCases`) dependen de interfaces de repositorio (`Domain/Repositories`), no de PDO directamente; los adaptadores concretos viven en `Infrastructure/Persistence`. Esto es lo que hace "hexagonal" a la arquitectura: se podría cambiar MySQL por otro motor implementando la misma interfaz, sin tocar casos de uso ni controllers.
- `Mailer` sigue el mismo patrón "intercambiable" que `AI_PROVIDER`/`PAYMENT_PROVIDER`: en local (`MAIL_HOST` vacío) escribe el correo en `/storage/mails` en vez de enviarlo, para poder probar verificación/recuperación sin SMTP real.

## Catálogo (Fase 3)

- Mismo patrón hexagonal que Auth: `Domain/Repositories/{Category,Brand,Product,Service}RepositoryInterface` → adaptadores PDO en `Infrastructure/Persistence` → UseCases en `Application/UseCases/Catalog` solo donde hay lógica real (slug único, validar categoría/marca/ciclo, subir imagen, reemplazar variantes/atributos) → Controllers.
- **Un solo endpoint público/privado por recurso**: `OptionalAuthMiddleware` intenta adjuntar el usuario si hay un JWT válido pero nunca lanza 401; el controller decide con `AccessChecker::can()` si debe incluir borradores/inactivos. Evita duplicar rutas `GET /admin/...`.
- **Slugs deterministas**: `SlugGenerator::unique()` recalcula el slug a partir del nombre en cada `create`/`update`, excluyendo el propio id de la comprobación de unicidad. Si el nombre no cambió, el slug generado coincide con el actual (no genera saltos de sufijo innecesarios); si cambió, se re-genera con sufijo `-2`, `-3`… solo si hay colisión real.
- **Reemplazo total en vez de CRUD granular** para variantes/atributos de producto (`PUT .../variants`, `PUT .../attributes`): son listas pequeñas que el formulario de edición envía completas, así que un `DELETE + INSERT` transaccional es más simple que sincronizar altas/bajas/ediciones una por una.
- **`stock_status` calculado, no almacenado**: se deriva de `stock`/`min_stock` en el momento de leer (`agotado` / `ultimas_unidades` / `disponible`), para no tener un campo que se pueda desincronizar del stock real.
- **`UploadedFileValidator` + `FileStorage`** (`Application/Support`) son compartidos entre avatares (Fase 2) e imágenes de catálogo (Fase 3): misma validación de extensión/MIME real/tamaño y el mismo patrón de guardado fuera del docroot con nombre aleatorio, sin duplicar la lógica.

## Búsqueda y favoritos (Fase 4)

- **Filtro vs. relevancia son dos cosas separadas**: el `WHERE` que decide qué filas entran usa `LIKE` palabra por palabra (`PdoProductRepository::buildSearchCondition()`) — así "casco deportivo" encuentra "Casco Integral Deportivo" aunque las palabras no sean contiguas. El **orden** cuando se pide relevancia usa `MATCH(...) AGAINST(... IN NATURAL LANGUAGE MODE)` sobre el índice `FULLTEXT` (migración `040`). Se decidió esta combinación porque `MATCH...AGAINST` solo en el `WHERE` fallaría para términos de menos de `innodb_ft_min_token_size` (3 caracteres, autocompletado incluido), y `LIKE` con la frase completa como único filtro es demasiado estricto para multi-palabra.
- **Parámetros nombrados únicos por ocurrencia**: `Connection.php` desactiva `PDO::ATTR_EMULATE_PREPARES`, así que MySQL usa *prepared statements* nativos, que no soportan reutilizar el mismo marcador con nombre más de una vez en la misma consulta (produce `SQLSTATE[HY093]`). Por eso cada palabra/columna de una búsqueda usa su propio nombre de parámetro (`search_0_name`, `search_0_sku`, …) aunque el valor bindeado sea el mismo.
- **`did_you_mean` compara contra palabras sueltas, no nombres completos**: comparar "kasko" contra "Casco Integral Deportivo" completo da una distancia de edición enorme; comparando contra la palabra "Casco" sola, `levenshtein()` la encuentra. `DidYouMeanFinder` es una función pura (sin acceso a BD); `GlobalSearchUseCase` arma el pool de palabras.
- **Favoritos reutilizan el patrón polimórfico** ya definido en la tabla `favorites` desde la Fase 1 (`favoritable_type` + `favoritable_id`); `PdoFavoriteRepository` hace dos consultas (productos y servicios) y las combina en PHP en vez de un `UNION` SQL, porque cada tipo tiene columnas propias (imagen, precio) que un `UNION` obligaría a normalizar artificialmente.

## Carrito y checkout (Fase 5)

- **Precio/stock en vivo, no el snapshot**: `cart_items.unit_price_snapshot` se guarda al agregar el ítem (referencia histórica), pero `PdoCartRepository::itemsWithLiveData()` siempre hace `JOIN` contra `products`/`services` para mostrar y calcular con el precio y el stock **actuales** — el snapshot nunca se usa para calcular totales, solo el checkout es quien decide qué precio se cobra realmente (sección 54).
- **Una sola fuente de verdad para el total**: `CartPricingCalculator::calculate()` es una función pura que usan tanto `GET /api/cart` (vista previa) como `CheckoutUseCase` (cálculo autoritativo). Si el total del carrito y el del pedido se calcularan por separado, un cambio en una de las dos fórmulas los desincronizaría silenciosamente.
- **La transacción del checkout vive en el repositorio, no en el UseCase**: `CheckoutUseCase` valida y arma los datos, pero `PdoOrderRepository::createFromCheckout()` es quien abre la transacción PDO, vuelve a bloquear cada producto con `SELECT ... FOR UPDATE` (re-verificación autoritativa de stock, no solo confía en lo leído antes de la transacción) y hace todos los `INSERT`/`UPDATE` (pedido, ítems, historial, pago, descuento de stock, `inventory_movements`, vaciar carrito). Como todos los repositorios de un mismo request comparten la misma instancia de `PDO` (`Connection::get()` es un registro por request, Fase 1), esto es seguro sin necesitar pasar la conexión explícitamente entre capas.
- **Carrito de invitado vs. autenticado**: se resuelven con la misma interfaz (`CartRepositoryInterface::resolveActiveCart(?userId, ?token)`); el token de invitado viaja en el header `X-Cart-Token` (no cookie, para no acoplarse a un dominio/frontend concreto todavía). `mergeGuestCartIntoUser()` se dispara desde `AuthController::login` (Fase 2, extendido) para no perder el carrito armado antes de iniciar sesión.
- **Envío con tarifa plana**: es un cálculo provisional (`CartPricingCalculator`) hasta que exista integración real con transportadoras (sección 51). Cambiarlo no debería afectar a `CheckoutUseCase` ni al esquema de `orders`.

## Frontend y documentación interactiva

El prompt maestro (sección 55) numera 12 fases pero ninguna se llama explícitamente "construir el frontend" — solo describe sus requisitos (secciones 39-41). Tras la Fase 5 el proyecto tenía una API completa pero ninguna página real la consumía. Se construyó un frontend funcional y Swagger en paralelo a las fases de backend, no como una fase numerada más:

- **Mismo origen, sin CORS**: el frontend se sirve desde la misma raíz que `/api/*` (`http://localhost/proyectos/castamotos/`), así que nunca hizo falta configurar CORS para desarrollo.
- **`<base href="/proyectos/castamotos/">` + rutas SIEMPRE relativas (sin "/" inicial)**: el sitio corre bajo un subdirectorio, no en la raíz del dominio. Una ruta como `/frontend/css/main.css` apuntaría a `http://localhost/frontend/...` (no existe) en vez de `http://localhost/proyectos/castamotos/frontend/...`. Cada página HTML/PHP declara `<base>` en el `<head>`, y todo (`<link>`, `<script src>`, `<img src>`, enlaces generados por JS, y `API_BASE` en `apiService.js`) usa rutas relativas que se resuelven contra ese `<base>` — `fetch()` y `window.location.href` también lo respetan. Es el único lugar a tocar si el despliegue cambia de subcarpeta (junto con `APP_URL` en `backend/.env`).
- **Vanilla JS, sin build step**: `<script>` clásicos en orden de dependencia (`helpers` → `apiService` → el resto de servicios → `layout`/`cards` → el script de la página). Los `const`/`function` de nivel superior de cada archivo quedan visibles para los `<script>` siguientes en el mismo HTML (mismo ámbito global del documento) — no hace falta un bundler ni módulos ES para este alcance.
- **`apiService.js` es el único que sabe hablar con el backend**: agrega `Authorization`/`X-Cart-Token` automáticamente y traduce la envoltura `{success, message, data|errors}` del backend a un valor de retorno o una excepción con `.fields`/`.status`. Todos los demás servicios (`authService`, `catalogService`, `cartService`) son adaptadores delgados sobre él.
- **URLs amigables resueltas en `.htaccess`, no en el router de PHP**: `/producto/{slug}`, `/categoria/{slug}`, etc. se reescriben a archivos HTML estáticos con querystring (`producto.html?slug=...`), consistentes con el `canonical_url` que la API ya devuelve desde la Fase 4 (sección 31).
- **La reescritura de `.htaccess` es invisible para el JS del navegador**: `RewriteRule` reescribe la petición del lado del servidor — el navegador nunca ve `producto.html?slug=...`, su barra de direcciones sigue mostrando `/producto/{slug}` y `window.location.search` llega vacío. Leer el slug con `new URLSearchParams(location.search)` (lo que hacían `producto.js`/`servicio.js`/`pedido.js`/`productos.js` antes de detectar este bug) funciona solo si se abre el `.html` directo con `?slug=...`, no por la ruta amigable real — por eso las páginas de detalle se veían vacías. Corregido con `helpers.routeParam(paramName, pathMarker)`: lee el último segmento de `location.pathname` (lo que el navegador sí ve) y solo si no aplica cae a `queryParam()`. Los parámetros que SÍ son querystring genuino en la URL navegada (`?search=`, `?on_sale=1`) siguen usando `queryParam()` sin cambios — la distinción es si el dato viaja en la ruta o en el querystring real.
- **`api-docs/` vive fuera de `/api/`** a propósito: así el `RewriteRule ^api/(.*)$ ...` de la raíz nunca la intercepta y Apache la sirve como estático sin pasar por el front controller del backend.
- **Riqueza visual de marketplace sin copiar la identidad de terceros**: el prompt maestro (sección 1) pide explícitamente negro/amarillo propios y prohíbe copiar el diseño de Mercado Libre — pero sí pide inspirarse en su experiencia de uso. Por eso el ajuste de diseño posterior a la Fase 6 tomó patrones de UX de marketplace (tarjetas con elevación al pasar el mouse, superficie clara detrás de la foto del producto para que resalte, insignia de descuento, estrellas de calificación, sidebar de filtros, migas de pan) manteniendo la paleta negro/amarillo y el logo propios — nunca los colores/tipografía/logo de un tercero.
- **El usuario en `localStorage` se refresca contra `/auth/me` en cada carga de layout, no solo se escribe en login**: `castamoto_user` (con el arreglo `roles` que decide si se muestra el link "Admin") originalmente solo se guardaba al iniciar/crear sesión. Si el rol de una cuenta cambiaba en el servidor, o si el navegador tenía guardada una sesión de una prueba anterior, el header quedaba mostrando (u ocultando) el link "Admin" con datos obsoletos indefinidamente — recargar la página no lo corregía porque nunca se volvía a pedir el usuario al backend. `authService.refreshUser()` llama a `GET /api/auth/me` (ya protegido por `AuthMiddleware`) y `initLayout()` la espera antes de pintar el header cuando hay token guardado; si el token ya no es válido, limpia la sesión en vez de dejarla en un estado inconsistente.

## Pedidos e inventario (Fase 6)

- **Máquina de estados como función pura**: `OrderStatusTransitions` (sección 22) no toca la BD — solo responde "¿se puede pasar de X a Y?", "¿es terminal?", "¿restituye stock?". `PdoOrderRepository::updateStatus()` la usa DENTRO de la transacción, después de bloquear la fila del pedido con `FOR UPDATE` y releer su estado actual — igual criterio que `createFromCheckout()` en la Fase 5: nunca confiar en un estado leído antes de entrar a la transacción, podría haber cambiado.
- **Reserva real sin romper el checkout ya probado**: en vez de rediseñar cómo `products.stock` se descuenta al comprar (Fase 5, ya verificado end-to-end), se le sumó `inventory.stock_reserved` como una capa adicional: se incrementa al crear el pedido, se libera al llegar a un estado terminal, y si la venta no se concretó (`CANCELADO`/`DEVUELTO`) además se restituye `products.stock`. Cada paso (`reservation`, `release`, `in`, `out`) queda en `inventory_movements` con su motivo — trazabilidad completa sin dos veces la lógica de "cuánto stock hay".
- **Ajustes manuales de inventario recalculan `products.stock` directamente** (no solo `inventory.stock_current`) porque ese es el campo que usan `stock_status`, los filtros de disponibilidad y el checkout desde las Fases 3-5 — mantener dos "fuentes de verdad" del stock físico habría sido un error; `inventory` guarda `stock_reserved` (lo nuevo de esta fase) y una copia de `stock_current` solo para lectura conjunta en `/admin/inventory`.
- **El panel `/admin` es deliberadamente mínimo**: dos tablas con acciones inline (cambiar estado, ajustar stock), sin las validaciones de UX más finas (ej. deshabilitar en el `<select>` los estados no alcanzables desde el actual) — esas mejoras y el resto del panel (usuarios, roles, cupones, reportes) llegan con la Fase 9. La seguridad no depende de lo que el frontend oculte: cada endpoint de `/api/admin/*` exige `AuthMiddleware` + `RequirePermissionMiddleware`.

## WhatsApp, gestión de servicios y galería 360° (post-Fase 6)

- **Número de WhatsApp como configuración, no como dato inventado**: `CONTACT_WHATSAPP_NUMBER` vive en `backend/.env` (nunca en el frontend) y se expone solo a través de `GET /api/settings/public` (`SettingsController`), la única ruta pública sin autenticación que devuelve configuración no sensible. Si queda vacío, `frontend/js/services/settingsService.js` devuelve `contact_whatsapp_number: ''` y el botón "Enviar pedido por WhatsApp" de `pedido.js` simplemente no se renderiza — nunca se muestra un número de ejemplo como si fuera real.
- **El mensaje de WhatsApp del pedido se arma con datos reales del pedido** (número, ítems, total ya calculados por el backend en el checkout), nunca un texto genérico — mismo criterio de "no inventar datos" que ya regía las reseñas/cuotas/cuentas regresivas.
- **Galería 360° = fotos reales + arrastre, no un modelo 3D**: no existen archivos `.glb`/`.gltf` de los productos, así que "ver en 3D" se resolvió con lo que sí hay — las fotos que subió el vendedor. `gallery360.js` (componente compartido entre `producto.js` y `servicio.js`) permite arrastrar para pasar de una foto a la siguiente, dando sensación de giro; con una sola foto no hay nada que rotar, así que el modo 360 (y su aviso "arrastra para girar") solo se activa con 2 o más imágenes.
- **Zoom con lupa + panel ampliado, y pantalla completa en táctil**: se replicó el COMPORTAMIENTO de zoom de un marketplace grande (sección 1 lo permite explícitamente: funcionalidad sí, diseño/paleta/logo de terceros no), implementado desde cero con CSS `background-position`/`background-size` — sin librerías externas. Solo se activa con mouse real (`matchMedia('(hover: hover) and (pointer: fine)')`) y solo si hay suficiente ancho de pantalla (≥1200px, el máximo de `.container`) para que el panel no se salga del viewport; en pantallas táctiles, donde no existe "hover", el equivalente es hacer click/tap sobre la foto para abrirla en pantalla completa (`.gallery-lightbox-overlay`), donde el usuario puede hacer pinch-zoom nativo del navegador (el `<meta viewport>` del sitio no lo bloquea). Las tres interacciones (girar, hacer zoom, abrir en pantalla completa) comparten el mismo `mousedown`/`mousemove`/`mouseup` en `initGalleryInteractions()` con un umbral de movimiento (`GALLERY_DRAG_THRESHOLD_PX`) para distinguir "fue un arrastre para girar" de "fue un click para ampliar" — sin esto, soltar el mouse después de girar también abriría la pantalla completa por accidente.
- **"Cómo llegar" usa el texto de `location` tal cual, sin geocodificar**: el enlace a Google Maps (`servicio.js::directionsLink()`) arma una búsqueda con la dirección exacta que escribió el vendedor — no hay geocodificación a latitud/longitud ni mapa embebido, evitando depender de una API de mapas de pago solo para esto.
- **Primera pantalla de administración de contenido (no solo de operación)**: hasta ahora `/admin` solo gestionaba pedidos e inventario — ya existentes en la BD desde el checkout o el seeder. El backend de servicios (`ServiceController`, CRUD + imágenes) ya estaba completo desde la Fase 3 pero sin ninguna interfaz que lo usara. La nueva pestaña "Servicios" es la primera que permite crear/editar contenido real del catálogo desde el navegador. Las imágenes solo pueden subirse DESPUÉS de crear el servicio (el endpoint de subida requiere un `service_id` real) — por eso, al crear, el formulario pasa a modo edición sin cerrarse, en vez de obligar a un segundo viaje al listado.
- **Borrado de imagen ahora también borra el archivo físico**: al construir la pantalla de imágenes se encontró que `PdoServiceRepository::deleteImage()` y `PdoProductRepository::deleteImage()` solo borraban la fila de `service_images`/`product_images`, dejando el archivo huérfano en `storage/uploads/*` para siempre. Se agregó `FileStorage::delete()` (idempotente: no falla si el archivo ya no existe) y ambos repositorios lo llaman después de confirmar el borrado en BD — corregido para productos también, aunque el bug se detectó por el trabajo en servicios, porque es el mismo patrón de código.
- **Gestión de productos, simétrica a la de servicios**: mismo criterio (el backend ya tenía el CRUD completo desde la Fase 3, solo faltaba la interfaz). Diferencia clave: el campo `stock` del formulario de producto se deshabilita al EDITAR (no al crear) — `products.stock` es la única fuente de verdad que usan `stock_status`, el checkout y `/admin/inventory` desde las Fases 3-6; dejar que este formulario también lo cambie habría creado una segunda vía para modificar stock sin pasar por `inventory_movements` (la trazabilidad de la Fase 6). Los productos también soportan imagen "principal" (`is_primary`, a diferencia de servicios que no distinguen orden) — el admin puede marcar cuál foto usa `productCardMarkup()` en las grillas.

## Modo claro/oscuro (post-Fase 6)

- **Todo el sistema de color ya vivía en variables CSS** (`:root` en `main.css`), así que el modo claro se implementó redefiniendo esas variables bajo `[data-theme="light"]`, sin tocar ninguna regla de color individual. Se separaron dos categorías de tokens que antes estaban mezclados bajo el mismo nombre:
  - **Fijos** (mismo valor en los dos temas): `--amarillo` y derivados (identidad de marca), `--negro` (texto que necesita contraste sobre amarillo/blanco, ej. `.btn-primary`), `--exito`/`--error` (semántica de estado).
  - **Por tema** (se redefinen en `[data-theme="light"]`): `--fondo` (fondo de página/header — nuevo, antes confundido con `--negro`), `--negro-suave`/`--gris-oscuro` (superficies), `--gris-borde*`, `--gris-texto*`, `--blanco` (texto principal — se vuelve oscuro en modo claro pese al nombre; renombrarlo habría obligado a tocar cada uso en `main.css` y en el HTML generado por los ~15 archivos JS de páginas, un costo desproporcionado para lo que pedía el cambio).
  - Se encontraron y corrigieron 3 lugares que combinaban un fondo oscuro FIJO (insignias/botones flotando sobre una foto: `.card__favorite`, `.admin-image-list__remove`, `.gallery-360-hint`) con `color: var(--blanco)` — al flipearse `--blanco` en modo claro, ese texto se habría vuelto invisible (oscuro sobre oscuro). Se fijaron a blanco literal con un comentario explicando por qué no usan la variable.
- **Sin parpadeo de tema al cargar**: `frontend/js/theme-init.js` es un `<script>` normal (no `defer`) colocado en el `<head>` de cada página justo después de `<link rel="stylesheet">` — bloquea el render hasta aplicar `data-theme="light"` si esa es la preferencia guardada, antes de que el navegador pinte nada. `frontend/js/services/themeService.js` (cargado con el resto de servicios) tiene la lógica completa del botón — `layout.js` pinta el botón 🌙/☀️ en el header y alterna+persiste en `localStorage` (`castamoto_theme`).
- **Oscuro sigue siendo el tema por defecto** (identidad de marca del prompt maestro): sin preferencia guardada, el sitio arranca oscuro; el usuario puede cambiar a claro y la elección se recuerda entre visitas.
- **Paleta clara corregida a grises neutros**: la primera versión usaba tonos beige (`#f7f6f3` de fondo) que se veían "sucios"/apagados. Se cambió a la estructura de color que usan los marketplaces grandes en su modo claro — fondo de página gris neutro (`#ebebeb`), tarjetas blanco puro, texto casi negro — aplicada sobre la paleta propia negro/amarillo (sección 1: se toma la estructura genérica de color, no ninguna paleta de marca de terceros).

## Panel admin con barra lateral, pedidos por acción y varias mejoras (post-Fase 6, 2ª ronda)

- **Barra lateral en vez de pestañas horizontales**: `/admin` pasó de `<div class="admin-tabs">` (4 botones en fila) a un layout `.admin-shell` con `<aside class="admin-sidebar">` fija en escritorio y cajón deslizable (`.is-open` + backdrop) en pantallas ≤900px — patrón estándar de dashboard. Las 4 secciones (`#admin-tab-orders` etc.) y sus IDs internos no cambiaron, así que toda la lógica de carga de datos de cada pestaña siguió intacta; solo cambió `wireTabs()` → `wireSidebar()` (selector `.admin-nav-link` en vez de `.admin-tab`, más apertura/cierre del cajón). Cada cambio de sección dispara una animación de entrada corta (`.admin-panel-enter`, fade + slide).
- **Cambio de estado de pedido = un botón por acción válida, no un selector con 9 estados**: antes el admin veía un `<select>` con TODOS los estados posibles (confuso — ¿cuál es el que sigue?). Ahora `OrderStatusTransitions::nextStates()` (nuevo método, misma máquina de estados de la Fase 6) calcula a qué estados se puede avanzar desde el actual, y `AdminOrderController` lo agrega como `next_statuses` en cada pedido — el frontend solo pinta un botón por cada uno (`helpers.orderActionLabel()`: "Confirmar pago", "Marcar en camino"...), destacando el primero como acción principal y coloreando en rojo con confirmación las irreversibles (`CANCELADO`/`DEVUELTO`). Ni el frontend duplica el grafo de transiciones ni el admin tiene que adivinar cuál de 9 opciones es la correcta.
- **Admin entra directo al panel al iniciar sesión**: `layout.js` revisa `isAdminUser(data.user)` justo después del login y redirige a `admin` en vez de recargar la página pública que se estaba viendo — el resto de usuarios sigue con el recargo normal.
- **Carrusel de fotos reales en el home**: `frontend/js/components/carousel.js` (auto-avance, flechas, puntos, pausa al pasar el mouse) arma sus slides con productos en oferta reales (`on_sale=1`) y, si no hay ninguno todavía, con los más nuevos — nunca con una promoción inventada; si no hay ningún producto publicado, la sección simplemente no se pinta.
- **Máximo 6 fotos por producto/servicio, validado en el backend**: `app.uploads.max_images_per_catalog_item` (config, default 6) se revisa en `UploadProductImageUseCase`/`UploadServiceImageUseCase` ANTES de guardar el archivo — nunca basta con que el frontend deshabilite el botón, cualquiera que llame la API directo debe respetar el mismo tope. El input de fotos del panel admin ahora acepta selección múltiple (`multiple`) y sube los archivos en secuencia respetando el cupo restante.
- **Bug encontrado de paso: borrar un producto/servicio no borraba sus fotos**: `PdoServiceRepository::delete()` / `PdoProductRepository::delete()` solo marcaban `deleted_at` en la fila del producto/servicio — las filas de `product_images`/`service_images` y sus archivos en `storage/uploads/*` quedaban huérfanos para siempre (mismo bug de fondo que el de borrar una imagen individual, corregido la ronda anterior). Ahora `delete()` borra los archivos físicos y las filas de imágenes ANTES del soft-delete del producto/servicio.
- **Latitud/longitud opcionales en servicios** (migración `042_add_coordinates_to_services_table`): si están cargadas, el enlace "Cómo llegar" del detalle apunta al punto exacto (`servicio.js::directionsLink()`) en vez de depender de que Google Maps interprete bien el texto de la dirección; el panel admin tiene un botón "Usar mi ubicación actual" que llama a la Geolocation API del navegador (funciona en `http://localhost` porque los navegadores tratan a `localhost` como contexto seguro aunque no sea HTTPS). El campo `location` de texto libre sigue siendo la fuente principal — las coordenadas son un plus, no un reemplazo.

## Módulo de reservas y dashboard con gráficas (post-Fase 6, 3ª ronda)

- **La reserva de un servicio EXTIENDE el carrito/checkout ya existente, no es un sistema paralelo**: en vez de crear tablas y flujos nuevos, se agregó `scheduled_at DATETIME NULL` a `cart_items`/`order_items` (migración `043_add_scheduled_at_to_cart_and_order_items`) — siempre `NULL` en items de producto, obligatorio para items de servicio. El pedido resultante ES la reserva: reutiliza order_number, estado, historial y los botones "siguiente paso" del panel admin ya construidos — nada de esto se duplicó.
- **Cada servicio agregado al carrito es su propia fila, nunca se combina sumando cantidades**: a diferencia de un producto (agregar el mismo dos veces suma cantidad), agendar "2x corte de cabello" en una sola fila no representa dos citas reales — `AddCartItemUseCase::addService()` siempre inserta una fila nueva y exige `scheduled_at` futuro (valida con `strtotime()`, sin una regla "date" en el `Validator` propio del proyecto).
- **Anti-doble-reserva con el mismo criterio que el anti-sobreventa de stock (Fase 5/6)**: `PdoOrderRepository::createFromCheckout()` re-verifica DENTRO de la transacción (mismo patrón que el `SELECT ... FOR UPDATE` de stock) que ningún otro pedido no cancelado tenga ya ese `service_id` + `scheduled_at` exactos, justo antes de insertar — un conflicto detectado ahí revierte todo el pedido con un mensaje claro. Es la misma limitación de fondo que el chequeo de stock existente (no es aislamiento serializable real, es un re-chequeo best-effort dentro de la transacción) — se documenta el trade-off en vez de fingir una garantía más fuerte de la que realmente hay.
- **Reservas del admin = una vista sobre order_items, no una tabla nueva**: `PdoOrderRepository::paginateReservationsForAdmin()` hace `SELECT` directo sobre `order_items` con `service_id`+`scheduled_at`, unido a `orders`/`users`, e incluye `next_statuses` con el mismo cálculo que `AdminOrderController` — la pestaña "Reservas" del panel reutiliza literalmente `adminService.updateOrderStatus()` y `nextStatusActionsMarkup()` de la pestaña "Pedidos", cambiar el estado de una reserva ES cambiar el estado de su pedido.
- **Dashboard "Resumen" con datos 100% reales, sin librería de gráficas externa**: `PdoDashboardRepository` agrega ingresos (hoy/30 días/histórico, excluyendo `CANCELADO`/`DEVUELTO`), pedidos por estado, serie de 14 días (con ceros en los días sin ventas, para que el eje no salte fechas), top 5 productos por unidades vendidas, conteo de stock bajo y reservas próximas — un solo endpoint (`GET /api/admin/dashboard/summary`) para una sola carga de página. Las gráficas (`frontend/js/components/charts.js`) son SVG armado a mano (barras verticales para la serie de ingresos, barras horizontales HTML/CSS para pedidos por estado) — cero dependencias nuevas, consistente con "vanilla JS, sin build step".
- **Bug de PDO encontrado al construir la serie de ingresos por día**: `PdoDashboardRepository::revenueByDay()` mezclaba parámetros nombrados (`:days`) con posicionales (`?`) en la misma consulta preparada — con `PDO::ATTR_EMULATE_PREPARES => false` (Connection.php) eso lanza `SQLSTATE[HY093]: mixed named and positional parameters`, no un resultado silenciosamente incorrecto. Corregido nombrando también los parámetros de estados excluidos (`:excluded_0`, `:excluded_1`, ...).

## Por qué estas decisiones

- **Sin framework pesado (Laravel/Symfony):** el prompt maestro pide PHP "puro" con arquitectura propia. Se construyó un micro-framework interno (Router, Kernel, Migrator) suficiente para las necesidades del proyecto, sin la sobrecarga de una dependencia grande.
- **Migraciones con archivos que devuelven una instancia anónima de `Migration`:** evita depender de convenciones de nombres de clase o autoload adicional fuera de `/src`, y es fácil de leer archivo por archivo.
- **`__route` vía querystring en lugar de `PATH_INFO`:** hace que el proyecto funcione igual dentro de una subcarpeta de XAMPP (`/proyectos/castamotos/`) que en un futuro vhost dedicado, sin tener que calcular un "base path".
- **Tablas `store_products` / `store_services`:** no están en el listado literal de la sección 34 del prompt maestro, pero son necesarias para que, cuando el marketplace permita múltiples vendedores, un mismo producto pueda ofrecerse desde varias tiendas con precio/stock propios.
